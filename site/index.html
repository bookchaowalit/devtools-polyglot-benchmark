Polyglot Benchmark Lab

Each language implements the same workloads. A lane has to pass the same contract tests before it is measured. Bars show the median of repeated runs, and the line on each bar spans min to max. Every number comes from a recorded run. A variant lane changes one thing against its parent and runs on the same machine, so it is shown as a percentage of the parent.

What these results cannot tell you

  • GitHub-hosted runners are shared VMs. Runs on different days can differ by more than the gap between lanes, so compare within one run.
  • The load generator and the server share one machine, each pinned to half the cores. A production host with its own network behaves differently.
  • Each lane uses its language's default libraries and one process. Tuned setups (more workers, faster JSON libraries, uvloop) would be new lanes, not these numbers.
  • Lanes use their runtime's default concurrency on the cores they are given (2). Go and Rust spread across both cores; one Node process and one uvicorn worker use one. That is the out-of-the-box behavior, not an equal-threads comparison.
  • In W4, PostgreSQL runs on the same VM and is not pinned, so the database competes for CPU with the server and the load generator. W4 shows how each driver and pool behaves under a shared bottleneck, not each language's ceiling.
  • W2 depends on whether a lane's SHA-256 uses the CPU's SHA extensions (OpenSSL in Python and Node; Go and Rust have their own implementations). Results can flip between CPUs.
  • The h11 multi-worker variant is slow for a protocol reason, not a CPU one: uvicorn's worker mode leaves TCP_NODELAY off and h11 writes headers and body separately, so Nagle's algorithm and delayed ACK add about 40 ms per request. The uvloop + httptools worker variant shows what workers gain without that.
  • Higher throughput on these workloads does not make a language the better choice for a product. Developer time, ecosystem, and hosting cost decide that.
